# Правила разработки «Живого бункера»

Этот документ дополняет [архитектуру игры](Архитектура.md) и [план реализации](План реализации.md). Его задача — сохранить понятную структуру кода по мере роста проекта. Примеры папок условные: после выбора движка они подстраиваются под его формат, а границы ответственности остаются теми же.

Рабочий выбор технологий и проверки этого выбора описаны в [технологическом стеке](Технологический стек.md).

Любой показываемый игроку текст создаётся по [правилам локализации](Локализация.md): через ключ и параметры, без фраз, вшитых в игровые правила.

## 1. Базовые правила

1. **Группировать код по игровой возможности**, а не складывать все классы одного типа в общие папки `Managers`, `Systems` или `Helpers`. Внутри `construction` находятся правила проектов, их исполнение, хранение и проверки.
2. **Каждое правило имеет одного владельца.** Экономика отвечает за резерв материалов, строительство — за этапы проекта, персонажи — за здоровье и навыки. Другие модули запрашивают действие через интерфейс владельца.
3. **Направление зависимостей одностороннее.** Игровые правила не знают о движке, кнопках, сети или базе данных. Внешние слои вызывают правила и отображают результат.
4. **Предпочитать простое прямое взаимодействие.** Вызов интерфейса подходит для ответа «можно ли и сколько стоит». Событие подходит для сообщения «это уже произошло» нескольким заинтересованным системам. Не превращать всё в события только ради универсальности.
5. **Данные контента отделены от правил.** Варианты кроватей, рецепты, бонусы биомов и параметры навыков описаны данными. Код определяет, как эти параметры применяются и какие ограничения действуют.
6. **Сложность добавляется после доказанной необходимости.** Начинаем с модульного монолита. Не создаём отдельный сетевой сервис, слой абстракции или фабрику для одной реализации без конкретной причины.

## 2. Предлагаемая структура проекта

```text
/
├─ Идея.md
├─ План реализации.md
├─ Архитектура.md
├─ Правила разработки.md
├─ Технологический стек.md
├─ Первый игровой час.md
├─ Перед реализацией.md
├─ Публикация.md
├─ Локализация.md
├─ Визуальный стиль и музыка.md
├─ Звуковой дизайн.md
├─ client/                    # представление, управление, звук, мини-игры
│  └─ src/
│     ├─ features/             # bunker_view, planning, expedition_ui ...
│     ├─ screens/              # сборка экранов из features
│     ├─ assets/               # исходные и подготовленные ресурсы клиента
│     └─ app/                  # запуск и конфигурация клиента
├─ server/                    # авторитетная игровая симуляция
│  └─ src/
│     ├─ modules/              # construction, characters, economy ...
│     ├─ app/                  # запуск, игровой цикл, сборка модулей
│     ├─ adapters/             # сеть, сохранения, системное время
│     └─ foundation/           # только действительно общие типы
├─ contracts/                 # версии сообщений между клиентом и сервером
├─ content/                   # предметы, рецепты, биомы, события, баланс
│  └─ locales/                # переводы ru и en
├─ tools/                     # проверка данных, миграции, редакторские утилиты
├─ tests/                     # сквозные сценарии и проверки сохранений
└─ docs/                      # решения по архитектуре и схемы при росте проекта
```

Кодовая база может использовать другие названия каталогов, если этого требует движок. Смысл структуры: файлы одной возможности ищутся в одном месте, а не по всему репозиторию. Документы, уже лежащие в корне, не нужно переносить ради схемы.

## 3. Структура одного серверного модуля

Пример для строительства:

```text
server/src/modules/construction/
├─ domain/            # Project, WorkStep, правила качества и допустимости
├─ application/       # CreateProject, ReplanRoom, CancelProject
├─ ports/             # нужные модулю интерфейсы: резервы, карта, задачи
├─ adapters/          # сохранение проектов, публикация обновлений
├─ content/           # схемы и проверка строительных определений
└─ tests/             # правила и сценарии именно этого модуля
```

**`domain`** хранит состояния и инварианты: нельзя завершить этап до его зависимостей, списать больше зарезервированного или повысить качество комнаты без выполненной работы. Он не импортирует движок, UI, сеть или код базы данных.

**`application`** выполняет игровую команду: проверяет права, получает нужные данные через `ports`, вызывает правила домена, фиксирует изменения и возвращает результат. Здесь находятся границы операции, а не формулы бонусов.

**`ports`** описывает, что модулю нужно от мира: например, `reserveMaterials(projectId, requirements)` и `isAccessible(cellId)`. Реализация этих вызовов принадлежит владельцу соответствующих данных или внешнему адаптеру.

**`adapters`** связывают модуль с хранением, сетью и движком. Замена формата сохранений не должна менять формулы строительства.

Если модуль пока мал, достаточно двух или трёх файлов. Папки появляются вместе с содержимым; пустую иерархию заранее не создаём.

## 4. Правила зависимостей между модулями

- Модули не читают и не меняют чужие внутренние таблицы, коллекции и объекты. Они используют публичные операции владельца.
- Циклические зависимости запрещены. Если `construction` нужен результат `economy`, а `economy` ждёт результат `construction`, общую операцию координирует слой приложения или один модуль реагирует на завершённое событие другого.
- Общее `foundation` содержит только устойчивые типы вроде `EntityId`, игрового времени, координат и результата операции. Правила лечения или постройки не становятся «общими утилитами».
- Контракты клиента и сервера описывают команды и видимые данные. Они не экспортируют серверные доменные объекты и не заставляют клиент понимать внутреннюю структуру симуляции.
- Прямые вызовы между модулями оформляются через узкие интерфейсы. События публикуются после успешного изменения состояния, имеют тип и версию и не используются для скрытой цепочки критичных синхронных проверок.

Пример: строительство спрашивает экономику о резерве стали и систему мира о доступности клетки. После завершения комнаты оно публикует `RoomCompleted`; интерфейс обновляет изображение, а система потребностей может пересчитать доступные места для сна. Проверка расхода стали остаётся в операции строительства и экономики, а не зависит от того, успел ли кто-то прочитать событие.

## 5. Паттерны для основных механик

| Задача | Паттерн | Как применяем |
| --- | --- | --- |
| Действие игрока | Команда / обработчик команды | `PlaceEquipment`, `StartExpedition`, `ReplanRoom` проходят проверку и дают явный результат |
| Долгая работа | Машина состояний | Проект: `planned → supplied → in_progress → blocked/completed/cancelled`; переходы проверяются правилами |
| Сложный приказ | Граф зависимых задач | «Построить кухню» превращается в расчистку, доставку, сети и установку оборудования |
| Производство и баланс | Определения на данных | Рецепты, стоимость, бонусы и требования редактируются без копирования веток кода |
| Несколько последствий | Событие после фиксации | `CharacterInjured` сообщает медицине и интерфейсу о завершённом факте |
| Сохранение | Снимок + журнал изменений | Незавершённая работа и расход материалов восстанавливаются после сбоя |
| Внешние системы | Порт и адаптер | Домен зависит от интерфейса времени или хранения, конкретная реализация подключается при запуске |
| Случайный результат | Явный источник случайности | Экспедиция и крафт получают результат от симуляции; тест может подставить известный исход |

Паттерн применяется, когда решает указанную проблему. Например, для простой формулы вместимости комнаты не нужны команда, событие и отдельный сервис — достаточно чистой функции в модуле комнат.

## 6. Правила моделирования состояния

**Состояния именуются явно.** Для предмета различаем `stored`, `reserved`, `carried`, `installed`, `destroyed`; для проекта — запланирован, выполняется, заблокирован, завершён, отменён. Не выводим важный статус из набора случайных флагов вроде `isDone`, `isPaused`, `hasWorker`.

**Инварианты проверяются в месте изменения.** Ресурс не может одновременно принадлежать двум складам, житель не может выполнять две несовместимые работы, комната не может давать бонус отключённого оборудования. Клиент может показывать предварительную проверку, но окончательная проверка выполняется сервером.

**Долгие действия переживают перезапуск.** Задание хранит прогресс, резервы и причину ожидания. После загрузки оно продолжается или корректно возвращается к безопасному состоянию.

**Числа имеют единицы.** Время, масса, объём, энергия, здоровье и игровые проценты обозначаются единицами и допустимыми диапазонами. Для процентов не смешиваем `0…1` и `0…100` в одном интерфейсе. Размеры помещений и расстояния используют одну систему координат.

**Ошибки пригодны для интерфейса.** Вместо общего «невозможно построить» команда возвращает код и данные причины: `missing_material`, `insufficient_skill`, `blocked_path`, `unstable_rock`, `no_power`. Текст для игрока формируется отдельно, чтобы его можно было менять и переводить.

## 7. Соглашения по файлам и именам

- Один файл отвечает за одну небольшую связанную задачу. Большой модуль разбивается по действиям и сущностям, но не по принципу «один метод — один файл».
- Имена в коде выбираются по игровому смыслу: `RoomProject`, `ReserveMaterials`, `TreatmentPlan`. Слова `Manager`, `Processor`, `Helper`, `Data` без уточнения избегаются.
- Публичная операция называется действием и объектом: `createProject`, `assignWorker`, `releaseReservation`. Событие называется завершённым фактом: `ProjectCreated`, `WorkerAssigned`, `ReservationReleased`.
- Комментарий объясняет причину необычного решения и важный инвариант. Обычное поведение выражается именем и кодом.
- Конфигурация запуска отделена от игрового баланса. Секреты и адреса сервера не хранятся в файлах контента.
- Временные эксперименты живут в отдельном прототипе или удаляются после проверки; они не остаются в основном коде как параллельная «новая версия» системы.
- Для визуальных и звуковых ресурсов храним исходник, экспорт, автора и право использования; временные материалы прототипа помечаем отдельно. Цветовые токены, состояния предметов и звуковые сигналы сверяем с [арт- и аудионаправлением](Визуальный стиль и музыка.md).

## 8. Изменение игрового контента и сохранений

Каждое определение предмета, биома, комнаты и рецепта имеет стабильный идентификатор. Ссылки на несуществующий идентификатор, отрицательный расход и невыполнимые обязательные рецепты выявляются проверкой данных до запуска игры. Наборы контента имеют версию.

Схема сохранения меняется через явные миграции. При удалении или переименовании типа предмета нужно решить, что станет с уже существующими экземплярами в старых мирах. Сохранения проверяются не только на загрузку, но и на продолжение игры после загрузки. Значимые изменения правил фиксируются в короткой записи решения в `docs/`, если они затрагивают несколько модулей.

## 9. Проверки изменений

Для каждой новой механики проверяем её главный риск, а не число тестов:

- **Правило домена:** стоимость, предел бонуса, переход состояния или невозможная комбинация.
- **Сценарий между модулями:** построить комнату из материалов, прервать снабжение, довезти ресурс и завершить работу.
- **Сохранение:** закрыть игру посреди действия, загрузиться и убедиться, что состояние не потеряно и ресурс не продублирован.
- **Сетевой контракт:** повторить команду, задержать сообщение и проверить единственный результат.
- **Производительность:** измерить дорогую систему на заранее выбранном масштабе поселения.

Перед включением изменения выполняются форматирование, статическая проверка, проверка данных контента, сборка и относящиеся к изменению сценарии. Полный длительный прогон нужен для изменений сохранений, сетевых правил и производительности. Метрики и журнал причин блокировки задач помогают искать проблемы без просмотра всех файлов проекта.

## 10. Порядок добавления новой возможности

1. Описать один наблюдаемый игровой сценарий и критерий готовности.
2. Выбрать модуль-владелец и данные, которые он хранит.
3. Определить команды, результаты и необходимые связи с соседними модулями.
4. Реализовать минимальное правило в домене и его вызов в приложении.
5. Добавить интерфейс, контент и сохранение изменённого состояния.
6. Проверить главный сценарий и отказные случаи, затем измерить нагрузку, если механизм работает часто.
7. Обновить архитектуру или запись решения, если поменялась граница модулей.

Такой порядок даёт команде понятное место для каждого нового файла и сохраняет игровые правила проверяемыми по мере роста проекта.
